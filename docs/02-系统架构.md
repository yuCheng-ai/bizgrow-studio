# 02. 系统架构

BizGrow Studio 的架构目标是：

```text
业务语义可配置
配置结果可校验
业务模板可发布
运行实例可推进
Agent 动作可约束
全流程可审计
```

---

## 1. 总体架构

```text
┌────────────────────────────────────┐
│  1. 用户交互层                      │
│  业务语义配置 / AI 生成 DSL / 预览  │
└────────────────────────────────────┘
                 ↓
┌────────────────────────────────────┐
│  2. BizDSL 层                       │
│  Object / Relation / State / Rule   │
│  Agent / Loop                       │
└────────────────────────────────────┘
                 ↓
┌────────────────────────────────────┐
│  3. 编译校验层                      │
│  Schema 校验 / 依赖校验 / 权限校验  │
│  冲突检测 / 版本管理                │
└────────────────────────────────────┘
                 ↓
┌────────────────────────────────────┐
│  4. 语义模型层                      │
│  本体 / 对象 / 关系图谱 / 状态机    │
└────────────────────────────────────┘
                 ↓
┌────────────────────────────────────┐
│  5. 运行时层                        │
│  Loop Runtime / Rule Engine         │
│  State Engine / Task Engine         │
└────────────────────────────────────┘
                 ↓
┌────────────────────────────────────┐
│  6. Agent 执行层                    │
│  上下文组装 / 工具调用 / 动作约束   │
│  人工确认 / 输出结构化              │
└────────────────────────────────────┘
                 ↓
┌────────────────────────────────────┐
│  7. 持久化层                        │
│  DSL 版本 / 对象数据 / 实例数据     │
│  事件日志 / 审计日志                │
└────────────────────────────────────┘
                 ↓
┌────────────────────────────────────┐
│  8. 集成层                          │
│  ERP / Excel / API / Webhook        │
│  文档 / SOP / 第三方系统             │
└────────────────────────────────────┘
```

---

## 2. 用户交互层

交互层不要以拖拽画布为核心。

推荐结构：

```text
左侧：场景 / DSL 文件 / 对象 / 模板 / 实例导航
中间：结构化配置区
右侧：自动解释区
底部：图谱 / 流程 / 实例模拟预览
```

核心交互：

```text
配置
→ 解释
→ 预览
→ 模拟运行
→ 发布模板
→ 生成实例
→ Agent 推进
→ 人工确认
→ 审计追踪
```

---

## 3. BizDSL 层

DSL 是系统内核，不是附属功能。

如果没有 DSL，系统会碎成一堆表单；如果全靠 Agent 自由生成，系统会不可控。

DSL 类型：

```text
Object DSL
Relation DSL
State DSL
Rule DSL
Agent DSL
Loop DSL
```

设计原则：

```text
声明式
非图灵完备
人可读
AI 可生成
机器可校验
可版本管理
可编译成运行模型
```

---

## 4. 编译校验层

编译校验层负责把 DSL 变成稳定模型。

需要做：

```text
语法校验
Schema 校验
对象引用校验
关系引用校验
状态转换校验
规则条件校验
Agent 权限校验
模板阶段校验
循环依赖检测
冲突检测
版本对比
```

示例：

```text
规则引用了 Inventory.availableQty，但 Inventory 对象没有该字段 → 编译失败
Agent 被允许执行 confirm_order，但 AgentPolicy 中禁止确认订单 → 编译失败
Loop 阶段输出 PurchaseRequest，但系统没有定义该对象 → 编译失败
```

---

## 5. 语义模型层

编译后的 DSL 进入语义模型层。

核心模型：

```text
OntologyConcept
BusinessObjectType
SemanticRelation
StateMachine
Rule
AgentPolicy
BusinessLoopTemplate
```

语义模型层要支持：

```text
图谱预览
影响分析
字段引用分析
规则依赖分析
Agent 权限解释
模板可运行性检查
```

---

## 6. 运行时层

运行时层是 BizRuntime。

它负责将业务闭环模板实例化为业务闭环实例，并推动实例向前运行。

核心模块：

```text
Loop Runtime
Rule Engine
State Engine
Task Engine
Event Engine
Audit Logger
Graph Query Service
```

运行流程：

```text
事件进入
→ 找到相关业务闭环实例
→ 加载实例上下文
→ 加载相关对象图谱
→ 评估状态机
→ 评估规则
→ 判断下一步可执行阶段
→ 若是系统动作：直接执行
→ 若是 Agent 动作：调用 Agent Executor
→ 若需要人工确认：生成任务
→ 写审计日志
→ 更新业务闭环实例状态
```

---

## 7. Agent 执行层

Agent 执行必须受控。

执行流程：

```text
选择 Agent
→ 加载 AgentPolicy
→ 加载可读对象
→ 裁剪上下文
→ 生成结构化 Prompt
→ 调用模型
→ 校验结构化输出
→ 权限检查
→ 是否需要人工确认
→ 执行动作或生成任务
→ 写审计日志
```

原则：

```text
Agent 不能直接越权执行。
Agent 的每个动作都必须经过权限守卫。
Agent 的关键动作必须进入人工确认。
Agent 的输出必须结构化。
Agent 的行为必须可审计。
```

---

## 8. 持久化层

第一阶段建议使用 PostgreSQL，不要过早上复杂图数据库。

原因：

```text
关系清楚
事务稳定
部署简单
能保存 JSONB
能做版本管理
后续可升级 pgvector / AGE
```

建议表分三类。

### 8.1 DSL 版本表

```text
biz_dsl_projects
biz_dsl_files
biz_dsl_versions
biz_dsl_publish_records
```

### 8.2 元数据表

```text
biz_ontology_concepts
biz_object_types
biz_fields
biz_relations
biz_state_machines
biz_state_transitions
biz_rules
biz_agents
biz_agent_policies
biz_loop_templates
biz_loop_stages
```

### 8.3 运行时表

```text
biz_object_instances
biz_object_links
biz_loop_instances
biz_tasks
biz_events
biz_audit_logs
biz_agent_runs
```

## 9. 集成层

第一版集成不要太重。

优先级：

```text
Excel 导入
CSV 导入
REST API Connector
Webhook
SOP / PDF 文档挂载
ERP 只读同步
```

后续再做：

```text
ERP 双向写入
采购系统写入
财务系统写入
MES / WMS 集成
```

## 10. 推荐技术栈

### 第一阶段

```text
前端：React + TypeScript + Vite
UI：Tailwind CSS
后端：Node.js + Fastify 或 NestJS
数据库：PostgreSQL
DSL：YAML + JSON Schema + Zod
规则：自研轻量规则引擎
状态机：自研状态机或 XState
Agent：模型接口抽象层
部署：Docker Compose
```

### 第二阶段

```text
图数据库：Neo4j / ArangoDB / PostgreSQL AGE
任务队列：BullMQ / RabbitMQ
持久工作流：Temporal
向量检索：pgvector
权限：Casbin / Oso
文档解析：Unstructured / LlamaParse / 自研解析器
```

---

## 11. 为什么不一开始用 Camunda

Camunda 很强，但它会把系统拉回 BPMN 轨道：

```text
流程图
流程节点
流程实例
审批流
```

BizGrow 的核心不是流程图，而是：

```text
业务语义
对象图谱
Agent 边界
业务闭环实例
```

可以借鉴 BPMN 的执行思想，但不要被 BPMN 绑架。

---

## 12. 为什么不一开始用 Neo4j

图谱重要，但第一版不一定需要图数据库。

第一版用 PostgreSQL 就能表达：

```text
object_types
object_instances
semantic_relations
object_links
```

图查询先做 2~3 层即可。

等关系追踪、影响分析、路径推理真的变复杂，再迁移图数据库。
